01 / 報告定位

AI的進度報告，要在你手上掌握

AI 替使用者做事時，應該在哪個通訊空間、用什麼方式，讓使用者掌握進度、成果與下一步？這份報告先分析即時通的大眾、辦公與特定市場，再理解各市場選用平台的理由，最後推導 AI 進度回報的產品設計。受眾是產品開發者與技術團隊；選型從市場需求出發。

03 / 使用者提例

台灣市場：工作與生活的界線

LINE、Teams、Slack
工具有不同定位

台灣市場的討論，著重 LINE、Teams 與 Slack。這些工具各有不同的市場定位，但在實際使用時，人們常把工作與生活混在一起：工作訊息進入生活群組，下班後仍持續處理公事。工具分開了，不代表人的使用習慣與溝通規則也分開了。因此，設計 AI 進度回報時，除了選擇通訊平台，也要釐清回報給誰、送到哪裡，以及什麼時候通知，才能尊重工作與生活的界線。

  1. 工作與生活的界線，也取決於人的使用習慣與溝通規則。

04 / 分析

大眾市場：人際網絡帶動選用

LINE、Messenger、WhatsApp、Viber、微信、QQ 與 KakaoTalk，是大眾通訊的代表工具。比較這個市場時，要看主要地區、客群、既有人際網絡與使用習慣。對應的 AI 產品機會包括個人的生活任務與資訊整理，回報重點是自己的事情做到哪裡、接下來需要做什麼。大眾普及程度可以支持生活服務的入口分析；工作任務的入口需要另外依辦公需求評估。

依據：LINE 海外事業與人口覆蓋率；WhatsApp 產品定位；Tencent：Weixin 與 WeChat；Tencent：QQ；Digital 2026 South Korea；Meta：Messenger 個人通訊；Viber 2023 年市場活動資料

05 / 分析

辦公市場：團隊與組織主導選用

Slack、Microsoft Teams、Google Chat、Zoom Chat、企業微信、釘釘與飛書，是辦公通訊的代表工具。分析這個市場，要看團隊如何選用、組織如何管理，以及工作資訊如何與既有流程整合。AI 回報需要交代任務歸屬、完成成果、阻礙、依賴關係與待決策事項。延續前面的台灣例子，團隊也可以選擇 Discord 作為工作空間；此時要從辦公需求分析它，而不能因為產品起於遊戲社群就排除它。

依據：Slack 產品與市場定位；Teams：透過 Workflows 接收 webhook 通知；Google Chat 產品定位；Zoom Chat 產品定位；Tencent：企業微信 WeCom；釘釘官方：工作與協作平台；飛書官方：團隊溝通與協作管理

06 / 分析

特定市場：逐一界定需求

特定市場需要再細分。Discord 起初服務遊戲玩家的聊天需求，之後加入遊戲直播。它的遊戲與社群定位、Telegram 的群組與頻道情境、Signal 的隱私訴求，各有不同的選用理由。iMessage 可從 Apple 裝置生態理解；Beeper 則是跨平台訊息聚合工具，屬於不同產品層次。這些需求不能合併成一個共同的占有率市場。分析 AI 回報時，先確認客群與用途；Discord 既可以服務社群，也可以在團隊選用下承接辦公協作。

依據：Discord 官方使用者概況；Telegram：Bots 開發說明；Signal 產品定位；Apple：iMessage、RCS 與 SMS/MMS；Beeper 通訊整合定位；Discord 官方沿革：2015 遊戲聊天、2019 Go Live

選型先確認這項 AI 任務服務哪個市場、由誰使用與決策，再理解為什麼選擇某個通訊空間。生活任務可以留在個人的生活工具；工作任務進入團隊選定的工作空間；社群任務進入對應的頻道或討論串。在這個基礎上，才決定回報內容、通知時機與互動方式，最後核對官方介面的可行性。生活與工作的區隔，是選型條件之一。

09 / 官方流程與設計解讀

要開始到能測通的難度也是不一樣的

要開始到能測通的難度
也是不一樣的

選好通訊空間之後，從開始設定到收到第一則 AI 通知，各平台的接入門檻也不一樣。LINE 要先註冊或登入帳號、建立官方帳號、啟用 Messaging API，再取得通道 Token 並試送。這裡的帳號驗證，不等於必須申請官方帳號的認證徽章。若已經有可管理的 Discord 伺服器或 Teams 工作空間，Discord 可以從設定建立 Webhook，Teams 則可從 Workflows 範本選擇頻道、完成登入授權並儲存，再以網址試送。兩者可以從既有空間的設定開始，比較的是單向通知入口，不代表完整雙向 Bot 只需點一下，也不代表本案已經實際測通。Slack 則是在既有工作空間建立 Slack App，啟用 Incoming Webhooks、選擇頻道並授權，再複製網址試送；若工作空間要求管理員核准 App，仍須依政策申請。接入門檻也是產品選型的一項條件。

  1. 比較範圍：第一次單向通知；Discord／Teams／Slack 已有帳號、工作空間與設定權限。
  2. LINE 不需認證徽章；Teams／Slack 仍受組織政策限制。依官方文件整理，尚未實際串接測通。

依據：LINE：Messaging API 開始設定；Discord：建立 Webhook；Microsoft：透過 Workflows 傳送 Webhook 訊息；Slack：建立 Incoming Webhook 與試送訊息

10 / 工程設計提案

任務狀態與通知狀態

任務完成
平台接受訊息
使用者已確認

這是三個需要分開記錄的事實。任務可能已完成，但訊息送出失敗；平台接受請求，也不等於使用者已閱讀。設計上以任務系統保存工作狀態，再追蹤通知結果。重送時保留同一事件識別，避免重複提醒。使用者回來查看時，看到的是最新狀態與更新時間，不只是一則可能過期的聊天訊息。

11 / 已查證介面與概念整理

即時通的進出通道

送出回報：AI → 即時通
接收回應：平台 Push → AI
主動取回：Pull；定時重複就是 Polling

從 AI 系統的角度看，即時通有送出與接收兩個方向。送出時，AI 可以透過平台 API 或通知 Webhook，把進度傳到使用者所在的頻道。接收時有兩種方式：一種是平台主動推送，透過 Webhook 或長連線，把新訊息與事件送給 AI；另一種是 AI 主動向平台查詢，這叫 Pull，定時重複查詢就是 Polling。接收資料也可能使用 Push，所以方向與傳輸機制要分開看。各平台支援的通道與權限不同；Telegram 的更新接收便提供長輪詢或 Webhook 兩種選擇。

  1. 以 AI 系統為觀察點；接收也可能使用 Push。各平台支援的方式與權限不同。

依據：Discord：Webhook Resource；Discord：Gateway 長連線、事件與權限；Telegram Bot API：接收更新、長輪詢與 Webhook；LINE Messaging API：訊息傳送

12 / 依官方介面提出的設計概念

Discord 的設計概念

AI 回報 → 團隊回覆 → AI 繼續處理
送出：Webhook／Bot API
接收：Bot Gateway 長連線

把進出通道套進 Discord，可以從單向通知開始，再加入雙向互動。只需回報進度時，串接程式可以使用頻道的 Incoming Webhook，不必先建立 Bot；也可以用 Bot API 傳送訊息。需要接收團隊回覆時，建立 Bot 並授權到指定工作頻道，由串接程式主動建立 Gateway 的 WebSocket 長連線。Discord 透過這條連線推送 Bot 有權接收的新訊息與事件，再交回 AI 處理。圖中的上方是回報出口，下方是回應入口，形成 AI 回報、團隊回覆、AI 繼續處理的循環。Gateway 需要心跳與斷線重連，訊息內容依頻道權限與必要的 Intents 開放。這是本案設計概念，尚未實際串接測通。

  1. 單向通知可只用 Webhook；雙向互動需 Bot、頻道權限與必要 Intents。
  2. Gateway 需維持心跳與斷線重連。本頁為設計概念，尚未實際串接測通。

13 / 官方介面與概念解說

Webhook 是什麼？

把上一頁送出回報的 Webhook 放大來看。Webhook 是一種通知方式：事件發生時，發送方把資料送到接收方指定的網址。在我們的 Discord 範例，接收方是 Discord，它提供一個連到指定頻道的 Incoming Webhook 網址。AI 程式有了新進度，例如報告已完成，就用 HTTP POST 把訊息內容送到這個網址，頻道裡便會出現這則回報。這條單向通知路徑不需要先建立 Bot。可以先記住三件事：誰送出、送到哪個網址、最後出現在哪個頻道。Webhook 網址含有可用來發送訊息的憑證，需要妥善保管。下一步就能建立這個入口，試著送出第一則通知。

  1. 此處指 Discord Incoming Webhook；單向通知不必先建立 Bot。
  2. 網址含發送憑證，需妥善保管；圖中訊息為示意，尚未實際串接。

依據：Discord：Webhook Resource

17 / 官方介面與設計解說

Bot 又是什麼？

前面用 Webhook 把進度送進 Discord。現在，如果團隊希望在頻道裡問目前進度，並自動得到回答，就可以用 Bot。Bot 可以理解成由程式控制的帳號。在 Discord 裡，它有自己的身分，依授權接收指令或事件，呼叫背後的程式，再回覆結果。例如成員發出查詢進度的指令，Bot 呼叫任務系統，取得進度後回覆頻道。如果需要理解自然語言或交給 AI 工作，也可以把 AI 接在後面。Bot 本身不等於 AI，它也可以只執行固定規則。能收到哪些訊息、能做哪些動作，則取決於平台介面、頻道權限與 Intents 設定。

  1. Discord Bot 依授權接收指令／事件；讀取一般訊息內容另受頻道權限與 Intents 限制。

依據：Discord 官方：建立第一個 Bot；Discord：Gateway 長連線、事件與權限

19 / 使用者提出的協作概念

讓進度回報，形成協作循環

整個概念，可以整理成四個環節。自動化執行，讓流程啟動、任務開始進行。AI 參與，協助整理資訊、分析判斷與產生成果。人為驗證，由人查看成果，確認內容、提出修正或下一步要求。最後是跟進處理，讓 AI 或程式接續執行，再回報結果，形成下一輪循環。即時通就是人與 AI 在這個循環中交接、確認與追蹤的共同入口。讓 AI 的進度報告，真正掌握在你手上。

  1. 自動化執行 → AI 參與 → 人為驗證 → 跟進處理 → 再次回報。

附錄二：官方通知介面與互動邊界

以下是官方文件可支持的入口與設計解讀，未在本案建立帳號連接或做端到端驗證。例子不代表所有平台都有相同的互動能力。

平台主動通知回覆與動作接入條件
LINE官方帳號的 Messaging API 可傳送 push 訊息。回覆及互動需接收事件，再由產品處理。收件關係、帳號設定、訊息額度與費用需按產品情境核對。
LINE Messaging API：訊息傳送
SlackIncoming webhook 可將外部事件貼入已設定的對話位置。需要回覆、按鈕或修改任務時，另設 Slack app 的事件與互動處理。先取得工作區安裝與存取權限；webhook 本身不完成任務授權。
Slack：Incoming webhooks
TeamsWorkflows 的 webhook 觸發器可把訊息送進聊天或頻道。可另設處理回應的流程；需依卡片與流程設計驗證。核對組織允許的流程、擁有者與連線身分。
Teams：透過 Workflows 接收 webhook 通知
Google ChatIncoming webhook 可送出單向非同步通知。官方明示 webhook 無法接收使用者互動；雙向互動需 Chat app。需可用的 Workspace 方案、空間與管理員設定。
Google Chat：單向 webhook 通知
DiscordIncoming webhook 可發布頻道／討論串訊息。互動元件需符合 application-owned webhook 等條件，並另實作回呼。純 webhook 的發訊成功不能當成使用者已確認。
Discord：Webhook Resource
Telegram可評估 Bot 作為收發進度的介面。使用者先傳訊或將 Bot 加入群組，產品再處理命令與回覆。Bot 無法任意主動對陌生使用者開啟對話。
Telegram：Bots 開發說明
