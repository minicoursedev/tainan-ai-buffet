# 任務移交摘要

產出讓接手者不必重讀整段對話，就能知道要改什麼、從哪裡開始、如何確認完成的摘要。以使用者目前的任務為主軸，按執行需要組織資訊。

## 選取內容

- 開頭明確寫出任務目標與預期行為。保留使用者指定的 repository、branch、沿用機制及交付要求。
- 把已完成的盤點轉成可執行清單：受影響檔案或入口、已確認問題、剩餘數量與證據位置。已有明確結論的事項，直接寫成待辦，不退回「是否有問題」「再盤點看看」。
- 區分已查證事實、推論及待查事項，標明查證範圍。靜態例外數量不等同已確認的 API 錯誤數量；單元測試通過不等同實際流程通過。
- 寫明目前修改狀態，包括未提交修改、已完成部分、仍未處理的根因與必要的測試限制。訊息或表面修正不能列為根因已解決。
- 保留會改變接手者操作的必要前提。沿用既有基礎的要求應指出可參照的程式或流程，不另造一套設定要求。
- 省略與本任務無關的分支、部署、對話爭議及歷史。使用者刪去的無關內容應直接移除，不改寫成「本次不包含某事」繼續佔據摘要。

## 組織移交

依任務規模使用短段落、清單或表格，通常包含以下資訊，不必建立空白章節：

1. **目標與工作位置**：具體成果、repository／branch，以及接手入口。
2. **已知現況**：盤點結果、證據連結與現有修改。提供足以開始的重點，避免只有文件連結。
3. **剩餘工作**：依依賴順序列出具體修改與必要查證，將未完成問題對應到檔案或行為。
4. **驗收與 checkpoint**：執行方式、應確認的結果、證據與進度保存位置。需要獨立重跑時，明列其完成條件。

檔案與執行入口應可直接定位；提供命令時核對現有腳本與參數。帳密只引用既有安全來源。若無法核對目前狀態，明示資訊來自先前紀錄，不把它描述為本次查證。

使用者要求文件時，更新或建立專案內適合位置的移交文件並提供連結。前置條件放在執行前，操作修正放在對應步驟，歷史只保留會影響理解的部分。指定同一份進度紀錄，讓接手者更新完成項目、待辦與證據。

## 執行邊界

移交文件應明確限制接手者的決策範圍。接手者的責任是完成已確認目標，不重新定義需求或擴張架構。

- 已確認的需求、規則與限制視為執行基準，不因接手者有其他設計偏好而重新評估。
- 優先在既有架構、資料模型與流程內完成需求；不得因改善程式品質而擴大重構範圍。
- 待查事項只授權查證，不等同授權自行制定新的產品規則或架構。
- 若完成需求必須改變已確認規則、增加新的架構層、改變資料模型或擴大至明顯無關範圍，應停止受影響部分的實作，將原因、影響與最小候選方案記入移交文件，交回上游決策；其他不受影響且仍符合既定範圍的工作可繼續。
- 不處理與完成本任務無直接必要性的 technical debt。



## 交付前核對

確認文件是否清楚區分「接手者可直接決定的實作細節」與「必須回交上游決策的需求／架構變更」。

從接手者角度檢查：能否直接找到工作位置、利用既有盤點開始修改、辨識尚未解決的問題，並執行驗收？刪除不影響以上決策的填充文字。

若使用者要求重訂計劃，依目標重新整理整份內容，清除舊版矛盾與失效指令；不要持續在尾端追加補充。完成聲明須與實際證據一致。
